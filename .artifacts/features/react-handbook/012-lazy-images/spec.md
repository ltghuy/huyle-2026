# Feature: Lazy-Loaded Images

## Overview

Practice 11 of the playground. Image-heavy pages (galleries, feeds, product
lists) waste bandwidth and slow down what the visitor actually sees when
every image is requested up front, and they jump around when images arrive
without reserved space. The learner wants to build lazy loading by hand:
start an image only when it nears the visible area, show a placeholder of
the right shape meanwhile, reveal it without a flash or a layout jump,
recover from failures, skip images the visitor flew past, and still load
the first visible images immediately.

The demo is a gallery of generated photos inside a scrolling viewport. The
learner can switch between the hand-built loader, the browser's built-in
lazy loading and loading everything at once, and compare live counters for
each: requests the server received, bytes served, requests cancelled, time
until the first visible images are shown, and layout shift. Cross-practice
rules from feature 001 apply: the core logic is hand-built, demo data and
images come from the project's own mock API with configurable latency and
failure injection, and the page has an explanation guide, demo controls
and a live demo.

## Goals

- [x] Images below the visible area are not requested until they come within a configurable distance of it: on first view the hand-built loader requests at most the visible images plus the preload band, while loading everything requests the whole gallery.
- [x] Every image shows a placeholder with its final shape while loading, so a gallery that reserves space has zero layout shift; the learner can turn the reservation off and see the shift measured.
- [x] Failures are visible and recoverable per image, and images scrolled past quickly are skipped or cancelled instead of downloaded.
- [x] The learner can compare the hand-built loader, native lazy loading and eager loading with live, measured numbers (requests, bytes, cancelled, time to visible, layout shift).

## Out of Scope

| Feature | Reason |
|---------|--------|
| Real photos, uploads or external image hosts | Images are generated by the project's mock API |
| Image formats and compression (WebP/AVIF conversion, quality settings) | Server-side image pipelines are a different topic; the guide mentions them |
| Lightbox, zoom, carousel | Not about loading |
| Virtualizing the gallery (removing off-screen tiles) | Practice 7 covers it |
| Lazy loading of iframes, videos or background images | Same idea; the guide mentions them |
| Bandwidth throttling of the response body | Latency and failures are enough to see the behavior; browsers' devtools throttle bandwidth |

## User Stories

### P1: Images load as they approach the viewport

- As a visitor, I want images to download only when I'm about to see them so that the page is fast and doesn't waste my data.
- **Why P1:** The pattern the practice is named after.
- **Independent Test:** Open the demo with the hand-built loader: the requests counter shows only the visible images plus those within the preload distance; scroll the gallery slowly: requests grow row by row, and each image appears before or shortly after it scrolls into view.

**Acceptance Criteria:**

- [x] AC-001: WHEN the practice opens THEN system SHALL load the gallery's photo list (title, description for screen readers, width, height, dominant color, tiny preview) from the mock API, showing a placeholder grid while loading and an error with Retry if it fails.
- [x] AC-002: WHILE the hand-built loader is active THEN system SHALL request an image only once its tile comes within the preload distance (none, 200 px or 600 px beyond the gallery viewport, chosen in the demo controls) and SHALL never request the same image twice in one run unless retried.
- [x] AC-003: WHEN an image has loaded THEN system SHALL finish decoding it before showing it, then reveal it with a short fade (instant under reduced motion), so no half-painted image is ever shown.
- [x] AC-004: WHEN the gallery is displayed THEN each image SHALL be offered in four widths (320, 640, 960, 1280 px) and the browser SHALL pick one for the tile's displayed width and screen density; each loaded tile SHALL show the width it got and its size in KB.
- [x] AC-005: WHEN the first N images (0, 3 or 6, chosen in the demo controls; default 3) are marked as priority THEN system SHALL request them immediately at high priority, without waiting for the observer or any delay.

### P1: Placeholders that reserve space

- As a visitor, I want a placeholder in the image's final shape so that the page doesn't jump while images arrive.
- **Why P1:** A lazy gallery without reserved space shifts the layout on every load.
- **Independent Test:** With "Reserve space" on, scroll the whole gallery with 1500 ms latency: the layout-shift counter stays at 0. Turn it off and repeat: the counter goes above 0.

**Acceptance Criteria:**

- [x] AC-006: WHILE an image is not shown yet THEN its tile SHALL show the chosen placeholder: blurred tiny preview ("Blur-up"), its dominant color, an animated skeleton (static under reduced motion), or nothing; the placeholder SHALL be hidden from screen readers.
- [x] AC-007: WHILE "Reserve space" is on THEN every tile SHALL have the image's final aspect ratio before it loads; WHEN it is off THEN tiles SHALL use a fixed placeholder height and resize when the image arrives, as a naive implementation would.
- [x] AC-008: WHILE the demo runs THEN system SHALL measure the layout shift caused inside the gallery (the browser's layout-shift score, which only counts what is on screen) for the current run, or say it can't be measured in this browser.

### P1: Compare strategies with live counters

- As a learner, I want to switch between the hand-built loader, native lazy loading and eager loading and see the numbers so that I know what each actually costs.
- **Why P1:** The comparison turns the technique into something measurable.
- **Independent Test:** Run each strategy from the top without scrolling: eager requests every image, native lazy requests what the browser chooses (typically more than the hand-built loader), the hand-built loader requests only the visible and preload images; the results table keeps one row per strategy.

**Acceptance Criteria:**

- [x] AC-009: WHEN the learner picks a strategy ("Hand-built", "Native lazy", "Eager") THEN system SHALL start a new run with that strategy: fresh image addresses (so nothing comes from the cache), counters at zero, gallery scrolled to the top.
- [x] AC-010: WHILE a run is active THEN system SHALL show live counters: requests the server received for this run, KB it served, requests cancelled before finishing, failed requests, images shown out of total, time until all images visible at the start were shown, and layout shift; the request, KB and cancelled numbers SHALL come from the server, not from the page's own guess.
- [x] AC-011: WHEN a run ends (strategy or setting change, Reset) THEN system SHALL keep its final numbers in a results table with one row per strategy (the latest run of each) next to the current run, so the strategies can be compared side by side.
- [x] AC-012: WHEN "Native lazy" or "Eager" is active THEN images SHALL use the same placeholders, sizes and space reservation as the hand-built loader, so only the loading strategy differs.

### P2: Errors and retry

- As a visitor, I want a failed image to say so and let me retry so that one bad request doesn't leave a hole.
- **Why P2:** Failure handling; the gallery works without it on a good network.

**Acceptance Criteria:**

- [x] AC-013: WHEN an image fails to load THEN its tile SHALL keep its placeholder shape, show "Couldn't load" with a Retry button that names the image, and count the failure.
- [x] AC-014: WHEN the learner retries one image or chooses "Retry failed" THEN system SHALL request it again with a new address (bypassing any cached failure) and reveal it on success.
- [x] AC-015: WHEN the learner changes latency (0–3000 ms) or failure rate (0–100 %) THEN the next image requests SHALL use them without restarting the run.

### P2: Skip images scrolled past quickly

- As a visitor, I want images I fly past not to be downloaded so that fast scrolling doesn't queue dozens of useless requests in front of the ones I stop at.
- **Why P2:** A refinement on top of basic lazy loading.

**Acceptance Criteria:**

- [x] AC-016: WHEN a start delay is set (off, 150 ms or 400 ms) THEN the hand-built loader SHALL request an image that came into range while scrolling only once scrolling has paused for that long with the tile still within the preload distance, and count tiles that left earlier as "skipped"; tiles already in range when the gallery opens SHALL start at once.
- [x] AC-017: WHEN a tile leaves the preload distance while its image is still downloading THEN the hand-built loader SHALL cancel the request (the server records it as cancelled), count it, and request it again if the tile comes back.
- [x] AC-018: WHEN the learner chooses "Fly through" THEN the gallery SHALL scroll smoothly from top to bottom in about two seconds (instantly under reduced motion), so the skipping and cancelling can be compared across strategies.

### P3: Accessible and responsive

- As a keyboard or screen-reader user, I want the gallery to be reachable and described so that lazy loading doesn't hide content from me.
- **Why P3:** Polish on a working gallery; required before done.

**Acceptance Criteria:**

- [x] AC-019: WHEN an image is shown THEN it SHALL have a meaningful text alternative and its title visible as a caption; a tile that is still loading SHALL be marked busy, and failures SHALL be announced politely in one place (not once per tile while scrolling) without moving focus.
- [x] AC-020: WHEN the gallery viewport has focus THEN the keyboard SHALL scroll it, and every control (strategy, settings, Retry, Fly through, Reset) SHALL be reachable by keyboard with a visible focus ring.
- [x] AC-021: WHEN the page is 360 px wide THEN the gallery SHALL show two columns, counters SHALL wrap, and the page SHALL not scroll horizontally; at wider sizes it SHALL show three columns.

## Edge Cases

- WHEN the learner switches strategy or setting while images are downloading THEN the old run's requests SHALL be cancelled or ignored and SHALL NOT change the new run's counters or tiles.
- WHEN an image finishes loading after its tile left the preload distance but before it was cancelled THEN it SHALL be shown (no wasted download).
- WHEN the browser can't decode an image THEN the tile SHALL show the failure state with Retry.
- WHEN the failure rate is 100 % THEN every tile SHALL end in the failure state and the gallery SHALL stay usable.
- WHEN latency is 0 THEN images SHALL still go through placeholder → reveal without flicker.
- WHEN the browser has no IntersectionObserver THEN the hand-built loader SHALL load all images (graceful fallback) and say so.
- WHEN the stats request fails THEN the server counters SHALL show their last value with a "stale" note; the gallery keeps working.
- WHEN the photo list fails to load THEN the gallery SHALL show an error with Retry, and the counters SHALL stay at zero.

## Success Criteria

- [x] On first view at the default settings (3 columns, preload 200 px, 3 priority images), the hand-built loader requests at most the images within one gallery viewport plus the preload band (≤ 12 of 48), while eager requests all 48.
- [x] Scrolling the full gallery with "Reserve space" on gives a layout-shift score of 0.00 for every strategy; with it off, the score is above 0.
- [x] "Fly through" with the hand-built loader and a 150 ms start delay requests at least 50 % fewer images than native lazy loading under the same latency.
- [x] Every image request in a run is counted by the server exactly once (no duplicate fetch when an image is revealed), and each cancel reaches the server as a cancelled request.
- [x] At 30 % failure rate, every failed tile can be recovered with Retry, and "Retry failed" leaves 0 failed tiles once the rate is set back to 0.
- [x] Zero serious or critical accessibility issues in both themes, and no horizontal page scroll at 360 px.

## Notes

- The explanation guide should cover: why lazy load (bytes, contention for connections, what's visible first), observing visibility with a margin and why a scrolling container must be the observer's root, placeholders and reserved aspect ratio (layout shift), decode before reveal, responsive widths chosen by the browser and why a lazy loader can give it the exact displayed width, priority for the first visible images (lazy-loading them delays the largest paint), skipping and cancelling on fast scroll, retry with a fresh address, how native lazy loading compares (no control over distance, no cancel), reduced motion and text alternatives.
- Numbers depend on the browser and window size; the counters measure what actually happened rather than estimating it.
