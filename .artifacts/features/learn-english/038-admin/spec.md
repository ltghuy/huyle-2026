# Feature: Admin page

## Overview

The owner runs the app from scripts on their own machine: `pnpm stats:report` for usage, `pnpm content:claims` for learners' claims, and edits to `content/*.json` plus `pnpm content:publish` for course content. Each needs the repo, a terminal and wrangler. The owner asked on 2026-11-09 for a private `/admin` page, open only to accounts marked as admins, to see how many learners there are and how active they are (today, this week, this month), decide claims, and add, change or remove content items.

## Goals

- [ ] The owner can see learner totals and activity for today, 7 days and 30 days without running a script
- [ ] The owner can approve or reject every pending claim from the page, and approved wordings reach learners without a publish
- [ ] The owner can add, change and remove content items from the page, live for learners at once, and no admin edit is ever lost or silently undone by the content scripts

## Out of Scope

| Feature | Reason |
|---------|--------|
| Making someone an admin from the page | Admins are set in D1 by the owner (`UPDATE user SET is_admin = 1 …`); a UI for it is a bigger security surface than one owner needs |
| Editing placement items and vocabulary sets | Placement items are generated by the publish script and sets embed their words; both are read-only here |
| Generating audio for new words or sentences | Audio is made by `pnpm content:audio` on the owner's machine |
| Claude's suggested verdicts on claims | Stays in `pnpm content:claims pull`; the app runs no AI |
| Charts | Numbers and tables are enough for one owner; can come later |
| Per-learner details (who did what) | Counts only, as the privacy page promises |

## User Stories

### P1: Only admins get in

**Acceptance Criteria:**

- [x] AC-001: WHEN the database is migrated THEN system SHALL add `is_admin` (default false) to the user table; it can't be set by any request from the browser
- [x] AC-002: WHEN a guest opens `/admin` THEN system SHALL ask them to sign in; WHEN a signed-in learner who isn't an admin opens it THEN system SHALL say "Bạn không có quyền vào trang này." and show nothing else
- [x] AC-003: WHEN any `/api/admin/*` route is called THEN system SHALL check the caller's `is_admin` in D1 on that request (not a cached session) and answer 401 or 403 with a Vietnamese message otherwise
- [x] AC-004: WHEN an admin is signed in THEN system SHALL show "Quản trị" in the sidebar; nobody else sees it
- [x] AC-005: WHEN search engines crawl THEN system SHALL keep `/admin` out of the sitemap and mark it noindex

### P1: Learners and activity

**Acceptance Criteria:**

- [x] AC-006: WHEN the admin opens "Tổng quan" THEN system SHALL show the number of accounts, accounts created today, in the last 7 days and in the last 30 days, accounts active today, in 7 days and in 30 days (by their last time in the app), and the number of pending claims
- [x] AC-007: WHEN the admin picks "Hôm nay", "7 ngày" or "30 ngày" THEN system SHALL show, for that range from the anonymous stats: devices per day, lessons completed, placement tests done, exercises answered per kind, the 10 words answered wrong most often, and Arena matches played
- [x] AC-008: WHEN days are counted THEN system SHALL use Vietnam time (Asia/Ho_Chi_Minh); the total counts every account, but learners who turned off anonymous stats are left out of the created and active counts, as in the stats report

### P1: Claims

**Acceptance Criteria:**

- [x] AC-009: WHEN the admin opens "Duyệt câu" THEN system SHALL list pending claims grouped by sentence and wording, oldest first, each with the Vietnamese sentence, the reference English, the wordings it already accepts, the claimed wording, how many learners claimed it and whether AI accepted it
- [x] AC-010: WHEN the admin approves a group THEN system SHALL add the wording to the sentence's accepted wordings (creating its wording item if needed), make it live for learners at once, and mark the group's claims approved
- [x] AC-011: WHEN the admin rejects a group THEN system SHALL ask for a short Vietnamese explanation (required) and mark the claims rejected with it, so learners see the one-time rejection notice as today
- [x] AC-012: WHEN a group's sentence no longer exists THEN system SHALL offer only "Bỏ qua", which marks the claims dropped

### P1: Content

**Acceptance Criteria:**

- [x] AC-013: WHEN the admin opens "Nội dung" THEN system SHALL list content items 50 per page, filterable by kind and level and searchable by id or text, showing id, kind, level, topic, whether it is removed, and whether it was edited here and not yet pulled into the repo
- [x] AC-014: WHEN the admin opens an item THEN system SHALL show its level, topic, sort and body (as JSON) for editing; placement and set items are shown read-only
- [x] AC-015: WHEN the admin saves an item THEN system SHALL check it with the same content rules as the publish script and, if valid, store it live with a new content version so learners' apps pick it up; WHEN it is invalid THEN system SHALL show each problem next to the body and save nothing
- [x] AC-016: WHEN the admin adds an item THEN system SHALL ask for kind, id and level, start the body from an example for that kind, and refuse an id that already exists
- [x] AC-017: WHEN the admin removes an item (after confirming) THEN system SHALL mark it removed with a new content version, as the publish script does, so learners keep their progress; a removed item can be restored
- [x] AC-018: WHEN the owner runs `pnpm content:pull [--remote]` THEN system SHALL write every item edited in admin back into the content JSON files (in the file that holds it, or `content/<kind>/<level>.json` for new ones; removed ones are taken out), then clear the "edited here" mark
- [x] AC-019: WHEN the owner runs `pnpm content:publish` while items edited in admin haven't been pulled THEN system SHALL stop before writing anything and say to run `pnpm content:pull` first

## Edge Cases

- WHEN two admin tabs save the same item THEN system SHALL keep the last save; each save is its own new version
- WHEN a claim group is decided from two tabs THEN system SHALL only change claims still pending, so the second decision changes nothing and says so
- WHEN the approved wording is already accepted THEN system SHALL mark the claims approved without adding a duplicate
- WHEN the content list query matches nothing THEN system SHALL say "Không có mục nào"
- WHEN an admin loses admin rights while the page is open THEN system SHALL answer the next request with 403 and show the no-access message
- WHEN an API call fails THEN system SHALL show the Vietnamese error and keep what the admin typed

## Success Criteria

- [ ] Every admin route is refused for a non-admin in tests
- [ ] A content edit made in admin survives `content:pull` + `content:publish` unchanged
- [ ] Each admin request stays within the Workers free plan (at most two D1 calls)

## Baseline

### Current Behavior

- Usage: `pnpm stats:report` prints anonymous counts and weekly account numbers.
- Claims: `pnpm content:claims pull` writes a review page; `apply` adds wordings to `content/wording/*.json` and marks claims in D1; a publish ships the wordings.
- Content: JSON files in git are the source of truth; `pnpm content:publish` makes D1 match them, removing rows missing from the files.

### Gaps / Limitations

- Everything needs the repo and a terminal; nothing can be done from a phone or quickly.
