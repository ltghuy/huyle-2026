# Decisions: Searchable Accordion

## Resolved

### Expansion mode

- **Decision:** Support both single and multiple modes, switchable in demo controls. Switching to single keeps the most recently opened section.
- **Rationale:** Practices both classic variants with one implementation.

### Search scope and feedback

- **Decision:** Search questions and answers; highlight matches; show "N of M sections match" and a "No results" state with Clear.
- **Rationale:** Matching answers finds more relevant help; highlights and counts make results trustworthy.

### Body-only matches in collapsed sections

- **Question:** Auto-expand wasn't selected, so how is a match hidden in a collapsed answer explained?
- **Decision:** A "match in answer" badge plus a one-line, highlighted snippet on the section header.
- **Rationale:** Explains every result without changing what the user opened.

### Matching rule

- **Decision:** All query words must appear (any order, in question or answer), case- and accent-insensitive, substring match. Results keep content order.
- **Rationale:** Forgiving for real users without a ranking engine.

### Extras

- **Decision:** Arrow-key navigation (Up/Down/Home/End), Expand all / Collapse all (multiple mode only, scoped to visible sections), grouping by category.
- **Not included:** URL sync, auto-expand on match.

### Content source

- **Decision:** About 40 FAQ entries (and a large set of about 400 for stress) from the project's mock endpoint with latency and failure controls; loaded once and searched in the browser.
- **Rationale:** Real loading/error states per the cross-practice data rule; server search belongs to practice 12.

## Tentative

### Large content set

- **Tentative Decision:** The large set is generated by repeating and varying the normal entries server-side.
- **Revisit when:** Generated text makes matches unrealistic.
